# Результаты проверки и замеров

Проверка выполнена 17 ноября 2026 года на Apple M5, 16 ГиБ памяти, macOS 26.6.2,
arm64. Компилятор — Apple Clang 21.0.0. Бенчмарк собран с C++17 и `-O2`.
Графики построены скриптом стандартной библиотеки Python, сторонние пакеты не использованы.

## Выполненный эксперимент

```sh
make benchmark
./benchmark 100000 3 17 results/benchmark.csv 10000000
make plots
```

Логическая длина фиксирована: N=10 000 000. Проверены семь размеров k:
100, 300, 1000, 3000, 10 000, 30 000, 100 000. Для каждого — случайный,
возрастающий и убывающий порядок вставки, три повтора, два хранилища.
В [benchmark.csv](benchmark.csv) сохранены 126 записей. Seed повторов — 17, 18, 19.
Для одинаковых N, k и seed все три порядка содержат одни и те же пары.

Измерено время полного пакета, а не одной операции. Построение, чтение, обновление
и удаление включают k обращений. В этом эксперименте чтение нулевых позиций тоже
включает k запросов. Map/Where/Reduce обрабатывают исходный вектор целиком по своему
контракту. Массовое построение включает подготовку и сортировку входных пар.

Генерация, подготовка копий для независимых операций, проверки значений, запись CSV
и печать находятся вне замеров. Для каждого повтора создаются новые векторы;
порядок запуска хранилищ чередуется. Все замеры прошли проверки результатов.
Дополнительно проверены парность строк, контрольные суммы и согласованность параметров CSV.

## Разбор результатов

Массив больше не пересоздаётся при каждом изменении int-записей: используется запас
ёмкости. Возрастающие вставки добавляют элементы в конец, поэтому этот режим существенно
дешевле случайных и убывающих вставок. Обратные вставки постоянно сдвигают уже накопленные
записи. Видимый квадратичный рост соответствует ожидаемой стоимости этих сдвигов.

Для удаления картина меняется: возрастающие индексы удаляются из начала массива,
а убывающие — из конца. Поэтому убывающее удаление быстро, а возрастающее требует
много сдвигов. Это разные нагрузки; результаты одного порядка нельзя распространять
на все операции.

AVL поддерживает логарифмическую высоту при любом порядке. Порядок влияет на константы
и локальность обращений, но не превращает дерево в цепочку.

Массовое построение массива заметно дешевле последовательных случайных Set: данные
сортируются один раз и размещаются без серии сдвигов. Эти результаты показаны отдельной
операцией, поскольку массовое построение и последовательность Set — разные алгоритмы.

При случайных запросах массив в этом запуске читает быстрее дерева. При упорядоченных
запросах в приведённой таблице дерево немного быстрее. Поэтому универсальный вывод
«массив всегда быстрее читает» измерениями не подтверждается.

Map и Where формируют упорядоченный набор результата; массив загружает его линейно,
дерево вставляет элементы с балансировкой. При случайном вводе и k=100 000 медиана Map
составляет 1.478 мс для массива и 9.969 мс для дерева. Reduce делает только обход:
0.318 мс и 2.697 мс соответственно. Перечислитель дерева дополнительно выделяет кадры стека.

Рост времени не является доказательством асимптотики. Системная нагрузка, частоты CPU,
работа кэшей и аллокатора отдельно не изолировались; прогрев отдельно не выполнялся.
Приведены медианы трёх повторов на одной машине, без утверждения о точных универсальных
отношениях скоростей. N в этом эксперименте не менялась; масштабирование измерялось по k.
Значение k=10^6 поддерживается параметрами, но в этом эксперименте не измерялось.

## Корректность

`make run_tests` проверяет оба хранилища одинаковыми сценариями: границы, нули, замену,
очистку, плотный ввод, массовое построение с повторными индексами, копирование,
перемещение, независимость результатов, Map/Where/Reduce и перечислители.

Случайные изменения вектора сверяются с независимой плотной моделью. Проверяются
AVL-инварианты после смешанных операций, словарь, сортированная последовательность,
повторное использование ёмкости массива, генерация и контроль результатов бенчмарка.
Отдельно проверяются все шесть порядков обхода дерева и доступ к текущему элементу
до начала и после конца перечисления.
Искусственные ошибки копирования проверяют сохранение данных и длины при исключениях.
Проверены int, double, complex, string и пользовательский тип без вывода в поток.
Проверки санитайзерами проходят без диагностик.

Отдельно проверены сценарии меню: оба хранилища, полный ввод и ввод пар, повторные
индексы, преобразования, сумма, переключение с сохранением данных, неверный ввод,
отрицательные индексы, переполнение, неудачная генерация, конец ввода и сравнение
с выгрузкой шести строк CSV. Дополнительный запуск прежних 17 групп тестов ЛР1
на обновлённых базовых заголовках также прошёл с санитайзерами.
